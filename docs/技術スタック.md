# タスク管理アプリ 技術スタック

このアプリで使う技術と、それを選んだ理由をまとめる。

次の3つは、はじめから決まっている条件である。それ以外の道具は、この3つに合わせて選んだ。

| 分類 | 使うもの |
| --- | --- |
| 画面（フロントエンド） | React |
| サーバー（バックエンド） | Java と Spring Boot |
| データベース | PostgreSQL |

Next.js は、今回は使わない（[1.1](#11-選ばなかったもの)）。

## 1. 第1段階（画面側）

| 分類 | 使うもの | 選んだ理由 |
| --- | --- | --- |
| 言語 | TypeScript | データの形を型で決めておくと、書き間違いをエディタが教えてくれる。仕事でもよく使われ、学習目的に合う |
| 画面の部品 | React | 画面を部品に分けて作れる。利用者が多く、調べたときに情報が見つかりやすい |
| 開発の道具 | Vite | 準備が簡単で、変更がすぐ画面に反映される。React と TypeScript のひな形がある |
| ドラッグ＆ドロップ | dnd-kit | カラム間の移動と並べ替えが作りやすい。キーボードでの操作にも対応している |
| 保存先 | `localStorage` | ブラウザに最初から入っていて、サーバーを用意しなくてよい（第1段階を作らなかったため、使っていない。[要件定義書](要件定義書.md) 1.4） |
| 見た目 | CSS | 追加の道具を使わず、CSS の基本を身につける |
| コードの点検 | Oxlint | Vite のひな形に含まれている。React の hooks のルール（依存配列のチェックを含む）とアクセシビリティ（jsx-a11y）のルールを入れ、警告も失敗として扱う。設定は `frontend/.oxlintrc.json` |
| 型のチェック | TypeScript（`tsc -b`） | `npm run check` で、Oxlint と一緒に実行する |
| 履歴の管理 | Git、GitHub | 課題の提出と、変更履歴の管理に使う |

### 1.1 選ばなかったもの

| 候補 | 選ばなかった理由 |
| --- | --- |
| Next.js | 今回は対象外とする。サーバーは Spring Boot で作るので、Next.js が持つサーバー側の機能は使いどころがない。画面は React と Vite だけで作れる |
| JavaScript | 手軽だが、型がないため間違いに気づきにくい |
| ESLint | 以前の Vite のひな形に入っていた点検の道具。今のひな形には Oxlint が入っているので、ひな形のまま Oxlint を使う |
| ブラウザ標準のドラッグ＆ドロップ | 並べ替えの位置の計算を自分で書く必要があり、キーボード操作にも対応しにくい |

## 2. 第2段階（サーバーとデータベース）

### 2.1 サーバー

| 分類 | 使うもの | 選んだ理由 |
| --- | --- | --- |
| 言語 | Java 25 | 長く手入れが続く版（LTS）で、Spring Boot が対応している |
| Java の本体 | Eclipse Temurin | 無料で使える Java の配布物。Windows 用のインストーラーがある |
| 枠組み | Spring Boot 4.0.8 | Java でサーバーを作るときの定番。設定が少なくて済み、日本語の情報も多い |
| 窓口（API）を作る部品 | Spring Web MVC（`spring-boot-starter-webmvc`） | [基本設計書](基本設計書.md) 3章の窓口を、JSON を返す形で作れる。Spring Boot に含まれている。エラーの返事は ProblemDetail（RFC 9457）の形にそろえる |
| 組み立ての道具 | Gradle | Spring Boot のひな形で標準になっている。プロジェクトに付いてくる `gradlew` で動くので、別にインストールしなくてよい |
| 入力のチェック | Bean Validation | 「タイトルは 100 文字まで」などのルールを、データの形に書き添えるだけでチェックできる（[画面設計](画面設計.md) 10章） |
| エラーの記録 | Logback | Spring Boot に最初から入っている。エラーをファイル（`backend/logs/taskmanagement.log`）に書き出す（[非機能要件](非機能要件.md) 4章） |
| 自動テスト | JUnit、MockMvc | Spring Boot のテストの部品に含まれている。窓口に HTTP で頼んだときの返事と、データベースの中身を確かめる |
| テスト用のデータベース | Testcontainers | テストのたびに Docker で PostgreSQL を立ち上げる。ふだん使うデータベースに触らずにテストできる。Spring Boot の `@ServiceConnection` で、つなぎ方を書かずに済む |
| コードの点検 | Checkstyle | Java のコードの点検の定番。Gradle に最初から点検の仕組みがある。ルールは `backend/config/checkstyle/checkstyle.xml`。あわせて、コンパイラの警告（`-Xlint:all`）も失敗として扱う |

### 2.1.1 自動の点検（GitHub Actions）

プルリクエストを作ったときと、main に取り込んだときに、GitHub Actions が自動で点検する（`.github/workflows/check.yml`）。

| 点検 | 実行するもの |
| --- | --- |
| 画面 | `npm run check`（Oxlint と型のチェック）、`npm run build` |
| サーバー | `./gradlew check`（Checkstyle、コンパイル、テスト） |

### 2.2 データベース

| 分類 | 使うもの | 選んだ理由 |
| --- | --- | --- |
| データベース | PostgreSQL 18 系 | 無料で使え、仕事でも広く使われている。UUID、日付、日時の型があり、[データ設計](データ設計.md) 3.3 のテーブルをそのまま作れる |
| データベースとのやり取り | Spring Data JPA | Java のクラスとテーブルを対応させて読み書きできる。入力した文字が命令として実行されるのを防げる。複数のカードの順番をまとめて変える処理（トランザクション）も、短く書ける |
| テーブルの変更の管理 | Flyway | テーブルを作る SQL を、番号付きのファイルとして残す。サーバーの起動時に、まだ実行していないファイルだけを自動で実行する（[非機能要件](非機能要件.md) 7章） |
| 起動の方法 | Docker Desktop と Docker Compose | PostgreSQL をパソコンに直接入れずに、決まったコマンド1つで起動、停止できる。設定をファイルに残せるので、手順書が短くなる |
| バックアップと復元 | `pg_dump` と `psql` | PostgreSQL に付いてくる道具。データベースの中身を1つのファイルに書き出し、そこから戻せる |

### 2.3 画面とサーバーのつなぎ方

第2段階でも、画面側の技術は第1段階と変えない。保存係だけを、サーバー用に差し替える。

| 分類 | 使うもの | 選んだ理由 |
| --- | --- | --- |
| サーバーへの通信 | `fetch` | ブラウザに最初から入っている。窓口が7つだけなので、追加の道具がなくても書ける |
| 開発中のつなぎ方 | Vite のプロキシ | 画面からの `/api` への通信を、Vite が Spring Boot へ取り次ぐ。画面とサーバーの番地（ポート）が違っても、ブラウザに通信を止められない |
| 接続を受け付ける範囲 | `server.address=127.0.0.1` | Spring Boot の設定で、同じパソコンからの接続だけを受け付ける（[非機能要件](非機能要件.md) 6章） |
| 接続情報の置き場所 | `.env` ファイル | データベースのパスワードを書くファイル。`.gitignore` に入れて、GitHub に上げない（[非機能要件](非機能要件.md) 6章） |

使う番地（ポート）は、次のとおりとする。

| 動かすもの | 番地 |
| --- | --- |
| 画面（Vite） | 5173 |
| サーバー（Spring Boot） | 8080 |
| データベース（PostgreSQL） | 5432 |

### 2.4 選ばなかったもの

| 候補 | 選ばなかった理由 |
| --- | --- |
| Maven | Gradle と同じ役目の道具。どちらでも作れるが、設定ファイルが短い Gradle にした |
| MyBatis、SQL を直接書く方法 | SQL の勉強にはなるが、書く量が増える。テーブルが3つと少ないので、Spring Data JPA で足りる |
| JPA にテーブルを自動で作らせる方法 | 手軽だが、テーブルをどう変えたかがファイルに残らない |
| PostgreSQL を Windows に直接入れる方法 | Docker なしで動かせるが、起動と停止に管理者の権限が要り、設定がパソコンの中に散らばる |
| axios | `fetch` で足りるので、道具を増やさない |
| Spring Security | ログインがなく、同じパソコンからしかつながないので、使わない |
| 画面の自動テスト（Vitest など） | 画面の動作の確認は手で行う（[要件定義書](要件定義書.md) 3.2） |

## 5. AWS で動かす

アプリを AWS の上で動かすときの技術。構成と手順は [AWS デプロイガイド](aws-deployment-guide.md) にまとめた。

自分だけが使うスクールの課題なので、仕事の Web アプリでよく使う構成より軽く、費用の安い構成にした。

### 5.1 道具

| 分類 | 使うもの | 選んだ理由 |
| --- | --- | --- |
| AWS の操作 | AWS CLI | マネジメントコンソールを手で操作せず、コマンドで操作できる。Claude Code にも頼みやすい |
| AWS へのログイン | IAM ユーザーのアクセスキー（MFA あり） | 手軽に始められる。ただし期限のない鍵なので、いずれ IAM Identity Center の一時的な鍵に切り替える |
| 構成をコードにする | Terraform | AWS の部品の作り方をファイルに残し、プルリクエストでレビューできる。`plan` で、変える前に下見ができる |
| Terraform の記録の置き場所 | S3（`use_lockfile`） | パソコンが壊れても記録を失わない。同時に 2 つの `apply` が走らないように鍵をかけられる |
| EC2 に入る | SSH（Windows に入っている OpenSSH） | 一般的で分かりやすい。22 番は自分の IP アドレスからだけ開ける |
| デプロイ | PowerShell のスクリプト（`deploy/deploy.ps1`、`deploy/smoke-test.ps1`） | Windows に最初から入っている。点検、ビルド、送る、入れ替える、確かめる、をコマンド 1 つで行い、失敗したら前の版に戻す |

### 5.2 AWS のサービス

| 分類 | 使うもの | 選んだ理由 |
| --- | --- | --- |
| サーバー | EC2 t4g.small（Amazon Linux 2023、Arm） | 2026-12-31 まで無料トライアルの対象。Spring Boot を動かすのに十分なメモリ（2GB）がある |
| 画面の配信と `/api` の取り次ぎ | nginx | パソコンでの Vite と同じ役目を、軽く確実にこなす。画面とサーバーを同じ EC2 に置ける |
| Spring Boot の起動 | systemd | 落ちたら起動し直し、EC2 を起動し直したときも自動で動き出す。Linux に最初から入っている |
| Java | Amazon Corretto 25 | AWS が配っている OpenJDK。Amazon Linux の `dnf` で入れられる。パソコンの Eclipse Temurin と同じ Java 25 |
| データベース | RDS for PostgreSQL 18（db.t4g.micro） | パソコンと同じ PostgreSQL 18。バックアップや更新を AWS に任せられる |
| データベースのパスワード | Secrets Manager（RDS が管理） | パスワードを RDS が作って置き、7 日ごとに自動で変える。Terraform の記録にもリポジトリにも残らない |
| ネットワーク | デフォルト VPC、セキュリティグループ | アカウントに最初からある VPC を使い、新しく作らない。通してよい相手を、IP アドレスとセキュリティグループで絞る |
| 費用の見張り | AWS Budgets | 月額の予算を超えそうなときに、メールで知らせる |

### 5.3 選ばなかったもの

| 候補 | 選ばなかった理由 |
| --- | --- |
| ECS（Fargate）と ECR | コンテナの管理まで AWS に任せられるが、ロードバランサーなどと合わせて月に数十ドルかかる |
| ALB（ロードバランサー）、CloudFront | 入り口を分けたり、配信を速くしたりできるが、使うのが自分だけなので要らない。費用もかかる |
| S3 と CloudFront で画面を配る | 画面とサーバーを分けられるが、まずはシンプルに、同じ EC2 に置く |
| EC2 の中で PostgreSQL を動かす | 費用は安いが、バックアップや更新を自分で行う必要がある |
| Systems Manager で EC2 に入る | 鍵を持たずに済むが、パソコンに別の道具が要る。SSH のほうが分かりやすい |
| HTTPS | 独自のドメインと証明書が要る。自分だけが使うので HTTP のままにした。そのため、HTTPS でしか使えないブラウザの機能（`crypto.randomUUID()` など）は使わない（#59） |
| GitHub Actions での自動デプロイ | SSH の入り口を自分の IP アドレスに絞っているため、GitHub からは入れない。手元のスクリプトで行う |
